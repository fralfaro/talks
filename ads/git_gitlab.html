Parte I

Git: control de versiones

¿Qué es Git?


git


Sistema de control
de versiones
distribuido


  • Control de versiones
    • Registra cada cambio en tus archivos a lo largo del tiempo.
    • Te permite volver a cualquier estado anterior.
  • Distribuido
    • Cada persona tiene una copia completa del historial.
    • Funciona sin conexión a internet.
  • Creado en 2005 por Linus Torvalds para el kernel de Linux.


🌿 Git no guarda tus archivos: guarda la historia de cómo llegaron a ser lo que son.

Guardar archivos ≠ versionar software


📁 Guardar copias 🌿 Versionar con Git
Archivos Muchos, con nombres inventados Uno solo, muchas versiones
Historial En tu cabeza Explícito y consultable
Motivo del cambio Se pierde Queda en el mensaje del commit
Autoría “creo que fue Ana” git blame lo dice exacto
Trabajo paralelo Imposible de combinar Ramas + merge
Volver atrás Buscar entre carpetas Un comando


💡 La diferencia clave: Git guarda cambios con contexto, no archivos sueltos.

Los tres conceptos que hay que entender hoy


📦 Repositorio

Tu proyecto más todo su historial.

Vive en la carpeta oculta .git/.

Si la borras, pierdes la historia (no los archivos actuales).

📌 Commit

Un punto de control: una foto del proyecto en un instante.

Tiene autor, fecha, mensaje y un identificador único (hash).

Siempre puedes volver a él.

🌿 Rama

Una línea alternativa de trabajo.

Te permite desarrollar algo nuevo sin tocar lo que ya funciona.

Crear una rama es instantáneo y gratis.


🎮 Analogía: el commit es un save point, la rama es una partida paralela, el merge es traer lo bueno de vuelta.

Modelo mental de Git


Todo lo que hagas con Git ocurre entre cuatro zonas:



🔑 Si entiendes este diagrama, entiendes el 80 % de Git.

Las cuatro zonas, una por una

  1. 💻 Working Directory — la carpeta que ves en tu editor. Aquí escribes código. Git observa, pero todavía no guarda nada.

  2. 📋 Staging Area (index) — la “antesala”. Con git add seleccionas qué cambios entrarán en el próximo commit. Puedes elegir solo algunos.

  3. 📦 Local Repository — con git commit los cambios pasan al historial de tu máquina. Ya son permanentes y recuperables. Aún nadie más los ve.

  4. ☁️ Remote Repository — con git push los envías al GitLab del Departamento. Recién ahí tu equipo puede verlos.


❓ ¿Para qué sirve el Staging Area? Para armar commits atómicos: si tocaste tres cosas distintas, puedes hacer tres commits coherentes en vez de uno llamado “cambios varios”.

El ciclo básico de trabajo



🔁 Este ciclo lo repetirás decenas de veces por semana. Que se te haga automático.

Los seis comandos que necesitas hoy


# 1. Traer el repositorio del equipo a tu máquina (una sola vez)
git clone git@gitlab.usm.cl:grupo-07/proyecto-ads.git
cd proyecto-ads

# 2. Ver el estado: qué cambió, qué está en staging, en qué rama estás
git status

# 3. Seleccionar cambios para el próximo commit
git add main.py            # un archivo
git add src/               # una carpeta
git add .                  # todo lo modificado (¡con cuidado!)

# 4. Guardar el punto de control
git commit -m "Agrega validación de RUT en registro"

# 5. Traer lo que hicieron los demás
git pull

# 6. Enviar tus commits al servidor
git push


💡 Regla práctica: git status antes y después de cada comando. Es gratis y te evita sorpresas.

Git

Ramas: trabajar sin romper nada

¿Qué es una rama?


Una línea de desarrollo independiente. Te permite construir algo nuevo mientras main sigue funcionando.


Trabajar con ramas


# Ver las ramas existentes (* marca la actual)
git branch

# Crear una rama y cambiarse a ella
git switch -c feature/login

# Cambiar entre ramas
git switch main
git switch feature/login

# Subir tu rama al remoto por primera vez
git push -u origin feature/login

# Integrar una rama en main (localmente)
git switch main
git merge feature/login

# Borrar una rama ya integrada
git branch -d feature/login


💡 git switch es la versión moderna de git checkout para cambiar de rama. Ambos funcionan; switch es más claro.

Convención de nombres de ramas


Prefijo Para qué Ejemplo

docs/ Documentación docs/manual-instalacion
refactor/ Reorganización interna refactor/capa-persistencia
test/ Pruebas test/cobertura-login

Merge vs. Rebase


🔀 git merge

Une dos ramas creando un commit de merge.

git switch main
git merge feature/login

✅ Conserva la historia real
✅ Seguro, no reescribe nada
❌ El grafo puede verse enredado

📏 git rebase

Reescribe tus commits sobre la punta de otra rama.

git switch feature/login
git rebase main

✅ Historial lineal y limpio
❌ Reescribe hashes
❌ Peligroso en ramas compartidas


⛔ Regla de oro: nunca hagas rebase de una rama que otra persona ya descargó. Para este curso: usa merge y déjate de problemas.

Conflictos: qué son y por qué ocurren


Ocurre cuando:

  • Dos personas modifican las mismas líneas del mismo archivo.
  • Git no puede decidir cuál versión es la correcta.


No ocurre cuando:

  • Editan archivos distintos.
  • Editan partes distintas del mismo archivo.
def calcular_promedio(notas):
<<<<<<< HEAD
    if not notas:
        return 0
    return sum(notas) / len(notas)
=======
    if len(notas) == 0:
        raise ValueError("Lista vacía")
    return sum(notas) / len(notas)
>>>>>>> feature/validacion


🧠 Un conflicto no es un error. Es Git diciéndote: “aquí hay dos decisiones humanas distintas, decide tú”.

Resolver un conflicto, paso a paso


  1. Git te avisa al hacer pull o merge: CONFLICT (content): Merge conflict in main.py

  2. Abre el archivo y busca los marcadores:

    • <<<<<<< HEAD → tu versión
    • ======= → separador
    • >>>>>>> otra-rama → la versión que llega

  3. Decide: quedarte con una, con la otra, o escribir una tercera que combine ambas.

  4. Borra los marcadores <<<<<<<, =======, >>>>>>>. Deben desaparecer por completo.

  5. Confirma la resolución:

    git add main.py
git commit -m "Resuelve conflicto en calcular_promedio"


💬 Ante la duda, habla con quien escribió la otra versión. El conflicto es técnico; la solución es de equipo.

¿Qué es GitLab?


🦊

GitLab


Plataforma DevOps
completa


  • Aloja repositorios Git en un servidor accesible para todo el equipo.
  • Gestiona el trabajo: Issues, Boards, Milestones.
  • Permite revisar código mediante Merge Requests.
  • Automatiza verificaciones con CI/CD Pipelines.

Primer acceso al GitLab del Departamento


  1. Ingresa con tu cuenta institucional (según indique el Departamento).

  2. Configura la autenticación para poder hacer push:

    • Opción A — SSH (recomendada): generas un par de claves y registras la pública en GitLab.
    • Opción B — Token: creas un Personal Access Token y lo usas como contraseña en HTTPS.

  3. Genera tu clave SSH (si eliges la opción A):

    ssh-keygen -t ed25519 -C "tu.correo@usm.cl"
cat ~/.ssh/id_ed25519.pub    # copia esta salida

  4. Pégala en GitLab: Avatar → Preferences → SSH Keys → Add new key.

  5. Verifica la conexión: ssh -T git@gitlab.<departamento>.usm.cl

⚠️ Si estás fuera del campus, es posible que necesites VPN institucional. Verifícalo antes de la primera entrega.

Merge Request: el corazón de la colaboración


Un Merge Request es una propuesta: “quiero integrar los cambios de mi rama a main; revísenlos antes”.


Qué permite:

  • Ver exactamente qué cambia (diff línea a línea).
  • Comentar líneas específicas del código.
  • Ejecutar verificaciones automáticas (pipeline).
  • Aprobar o pedir cambios.
  • Dejar registro de por qué se integró algo.
!14  Agrega validación de RUT en registro
─────────────────────────────────────────
De:    feature/12-validar-rut
Hacia: main

Autor:    @ana.perez
Revisor:  @juan.soto
Milestone: Entrega 1

✅ Pipeline passed (2 jobs)
✅ 1 approval
💬 3 threads (2 resueltos)

Closes #12

  [ Merge ]  [ Close ]


🔑 El MR es donde ocurre el aprendizaje del equipo: es donde se discute el código, no en el chat del grupo.

Crear un Merge Request, paso a paso


  1. Trabaja en tu rama y súbela:

    git switch -c feature/12-validar-rut
# ... editar, add, commit ...
git push -u origin feature/12-validar-rut

  2. GitLab te muestra un enlace en la terminal tras el push: “Create merge request”. También puedes ir a Merge requests → New.

  3. Completa el MR:

    • Source: tu rama · Target: main
    • Título descriptivo
    • Descripción: qué cambia, por qué, cómo probarlo
    • Closes #12 → cierra el Issue automáticamente al mergear
    • Assignee (tú) y Reviewer (un compañero)

  4. Espera el pipeline y la revisión. Responde los comentarios.

  5. Merge cuando esté aprobado. Borra la rama.

Revisión de código: qué mirar


🔍 Como revisor

  • ¿Entiendo qué hace este cambio?
  • ¿Resuelve realmente el Issue?
  • ¿Hay casos borde sin cubrir?
  • ¿Hay nombres confusos o código duplicado?
  • ¿Hay secretos o datos sensibles?
  • ¿Los tests prueban algo real?
  • ¿Está documentado lo necesario?

✍️ Como autor

  • MRs pequeños: menos de ~300 líneas se revisan bien.
  • Explica el porqué, no solo el qué.
  • Responde todos los comentarios.
  • No te lo tomes personal: se revisa el código, no a la persona.
  • Si no estás de acuerdo, argumenta — la revisión es conversación.


💬 Comenta el código, no a la persona. ❌ “esto está pésimo” → ✅ “¿qué pasa si notas viene vacío? Creo que revienta acá”.

Herramientas de revisión en GitLab


  • Comentario en línea — clic en el número de línea del diff. Queda anclado a esa línea exacta.

  • Suggestion — propones el cambio y el autor lo aplica con un botón:

    ```suggestion
if not notas:
    raise ValueError("La lista de notas no puede estar vacía")
```

  • Threads — cada conversación se resuelve explícitamente (Resolve thread). Un MR listo no debería tener threads abiertos.

  • Approve — aprobación formal. Se puede exigir N aprobaciones antes de mergear.

  • Draft MR — marca el MR como Draft: para pedir opinión temprana sin que se pueda mergear todavía.

CI/CD Pipelines: verificación automática



  • Un Pipeline ejecuta tareas automáticamente en cada push.
  • Se configura en un archivo .gitlab-ci.yml en la raíz del repositorio.
  • En el MR aparece un semáforo: ✅ verde o ❌ rojo.
  • Para el curso basta con lo esencial: que el código corra y que los tests pasen.
stages:
  - test

test:
  stage: test
  image: python:3.11
  script:
    - pip install -r requirements.txt
    - pip install pytest ruff
    - ruff check .          # estilo
    - pytest -v             # pruebas
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"


🤖 El pipeline es un revisor que nunca se cansa: revisa lo mecánico para que las personas revisen lo importante.

Prompts que sí funcionan


Mensaje de commit
“Este es el diff de mis cambios: [pegar git diff --staged]. Escribe un mensaje de commit en español siguiendo Conventional Commits, en imperativo, máximo 72 caracteres en la primera línea.”

Revisión previa
“Revisa este código como si fueras un revisor exigente de un Merge Request. Busca casos borde no cubiertos, errores de manejo de nulos y nombres poco claros. No reescribas el código: dime qué revisarías y por qué.”

Entender un conflicto
“Tengo este conflicto de merge [pegar el bloque con marcadores]. Explícame qué intentaba hacer cada versión y cuáles son mis opciones. No elijas por mí.”

Entender antes de ejecutar
“¿Qué hace exactamente git reset --hard HEAD~2? ¿Qué pierdo? ¿Hay forma de recuperarlo? Dame una alternativa más segura.”

Los riesgos que sí importan


  • 🔓 Filtración de secretos y código privado — pegar un .env, un token o código del proyecto en un chat externo puede ser una fuga de datos. Nunca pegues credenciales.

  • 🎭 Alucinaciones con aire de autoridad — la IA inventa comandos, banderas y APIs que no existen, con total seguridad. git push --force-with-safety no existe.

  • 💥 Comandos destructivos — un git reset --hard o un push --force mal aplicado borra trabajo del equipo. Entiende antes de ejecutar.

  • 🧠 Dependencia y pérdida de aprendizaje — si nunca resuelves un conflicto por tu cuenta, no aprendes a resolverlos. Y en la evaluación estás solo.

  • ⚖️ Atribución y honestidad académica — presentar como propio código que no entiendes es un problema de integridad, no de tecnología.

Las 5 reglas del curso


1️⃣ Nunca pegues credenciales, tokens ni archivos .env en una herramienta de IA.

2️⃣ Nunca hagas merge de código que no entiendes — lo hayas escrito tú, la IA o un compañero.

3️⃣ La IA no reemplaza la revisión humana: todo MR necesita la aprobación de un par.

4️⃣ Declara el uso de IA en la descripción del Merge Request, en la sección “Uso de IA”.

5️⃣ La responsabilidad del código es del equipo, siempre. La herramienta no responde por ustedes.


✅ Usar IA no está penalizado. Usarla sin entender lo que entregas, sí.

Cuando algo sale mal

Cómo deshacer errores comunes


Situación Comando Riesgo
Modifiqué un archivo y quiero descartarlo git restore archivo.py ⚠️ Pierdes los cambios
Hice add de más git restore --staged archivo.py ✅ Seguro
El mensaje del último commit está mal git commit --amend -m "nuevo mensaje" ⚠️ Solo si no hiciste push
Quiero deshacer un commit ya publicado git revert <hash> ✅ Seguro, crea un commit inverso
Necesito guardar cambios a medio hacer git stash / git stash pop ✅ Seguro
Me cambié de rama sin querer git switch - ✅ Seguro
Creo que perdí commits git reflog ✅ Casi todo es recuperable


🚨 Los dos comandos peligrosos: git reset --hard (borra trabajo local sin red de seguridad) y git push --force (puede borrar el trabajo de tus compañeros en el servidor). Ante la duda: pregunta antes de ejecutar.

Chuleta de comandos


Empezar

git clone <url>          # clonar
git init                 # iniciar repo
git remote -v            # ver remotos

Día a día

git status               # estado
git add <archivo>        # a staging
git commit -m "mensaje"  # guardar
git pull                 # traer cambios
git push                 # subir cambios

Explorar

git log --oneline --graph
git diff
git blame <archivo>
git show <hash>

Ramas

git branch                    # listar
git switch -c feature/x       # crear
git switch main               # cambiar
git merge feature/x           # integrar
git branch -d feature/x       # borrar
git push -u origin feature/x  # publicar

Deshacer

git restore <archivo>          # descartar
git restore --staged <archivo> # sacar de staging
git revert <hash>              # revertir publicado
git stash / git stash pop      # guardar temporal
git reflog                     # historial de todo
