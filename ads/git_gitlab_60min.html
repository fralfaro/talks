Git es el historial ordenado de tu proyecto


📁 Sin Git

Guardas copias del proyecto.

Cada copia es un archivo distinto.

El “por qué” de cada cambio se pierde.

🌿 Con Git

Cada cambio queda registrado: qué, quién, cuándo y por qué.

Puedes volver a cualquier punto.

Bloque 2

Git básico

¿Qué es Git?


Un programa que guarda la historia de tu proyecto


y te deja volver a cualquier punto de esa historia.


  • Se instala en tu computador y funciona sin internet.
  • No sirve solo para código: sirve para cualquier archivo de texto.
  • Es la herramienta estándar de la industria — la vas a usar toda tu carrera.

Las ocho palabras que hay que conocer


Palabra En simple
Repositorio Tu proyecto + toda su historia. Es una carpeta con un .git adentro.
Working directory Los archivos que ves y editas ahora mismo.
Staging area La “bandeja” donde pones los cambios que quieres guardar.
Commit Un punto guardado en la historia, con un mensaje que explica qué hiciste.
Branch (rama) Una línea de trabajo paralela, para no romper lo que ya funciona.
Remote La copia del repositorio que vive en GitLab, compartida con tu equipo.
Push Subir tus commits al remote.
Pull Bajar los commits que subieron los demás.

🧭 Son ocho palabras, no ochenta. Vuelve a esta tabla cada vez que te pierdas.

Cómo se mueven tus cambios



🔑 Si entiendes este dibujo, ya entendiste lo esencial de Git.

Los 7 comandos que necesitas


git clone URL_DEL_REPOSITORIO     # 1. traer el repositorio
git status                        # 2. ¿qué cambié?
git add .                         # 3. preparar los cambios
git commit -m "mensaje claro"     # 4. guardar el punto de control
git pull                          # 5. bajar lo del equipo
git push                          # 6. subir lo tuyo
git switch -c nombre-rama         # 7. crear una rama


👉 Ahora los vemos uno por uno: qué hace, cuándo se usa, un ejemplo y el error típico.

1️⃣ git clone


🔧 Qué hace

Copia el repositorio completo desde GitLab a tu computador, con toda su historia.

⏰ Cuándo se usa

Una sola vez por proyecto, al principio.

git clone URL_DEL_REPOSITORIO
cd proyecto-ads

❌ Error común: clonar dentro de otro repositorio, o clonarlo de nuevo cada vez que quieres actualizar.
✅ Para actualizar no se clona: se usa git pull.

2️⃣ git status


🔧 Qué hace

Te dice en qué rama estás, qué archivos cambiaste y qué está listo para guardar.

⏰ Cuándo se usa

Todo el tiempo. Antes y después de cada comando. Es gratis.

$ git status
On branch pantalla-login
Changes not staged for commit:
     modified:  src/login.py
Untracked files:
     nuevo_archivo.py

❌ Error común: no usarlo nunca y trabajar a ciegas.
✅ Si algo raro pasa, git status casi siempre te dice qué es y qué hacer.

3️⃣ git add


🔧 Qué hace

Pone tus cambios en la “bandeja” (staging area) para el próximo commit.

⏰ Cuándo se usa

Justo antes de hacer un commit.

git add .              # todo
git add src/login.py   # un archivo

❌ Error común: hacer git add . sin mirar y subir cosas que no correspondían (archivos gigantes, contraseñas, carpetas del entorno).
✅ Corre git status antes. Si agregaste algo por error: git restore --staged archivo.

4️⃣ git commit


🔧 Qué hace

Guarda un punto de control en la historia, con tu mensaje, tu nombre y la fecha.

⏰ Cuándo se usa

Cada vez que terminas algo que funciona. Mejor seguido y pequeño.

git commit -m "Agrega validación
   del formulario"

❌ Error común: un solo commit gigante al final llamado "cambios".
✅ El commit vive en tu computador hasta que hagas push. Commitear no comparte nada todavía.

Un buen mensaje de commit


❌ No ayudan

"cambios"
"asdasd"
"arreglo"
"ahora si"
"commit final"

Dentro de dos semanas, ni tú vas a saber qué hiciste.

✅ Ayudan

"Agrega pantalla de login"
"Corrige error al dividir por cero"
"Actualiza el README"
"Agrega validación del formulario"

Se entienden sin abrir el código.


📏 Regla simple: escribe qué hiciste, en pocas palabras. Si necesitas escribir “y”, probablemente son dos commits.

5️⃣ git pull


🔧 Qué hace

Baja a tu computador los commits que tus compañeros subieron a GitLab.

⏰ Cuándo se usa

Siempre antes de empezar a trabajar. Y antes de hacer push.

git pull

❌ Error común: trabajar toda la tarde sin hacer pull y después chocar con los cambios de todos.
✅ Si aparece un conflicto, no es un error: Git te está pidiendo que elijas. Lo vemos en el bloque 3.

6️⃣ git push


🔧 Qué hace

Sube tus commits a GitLab para que el equipo los tenga.

⏰ Cuándo se usa

Cuando terminaste algo y quieres compartirlo.

git push          # rama ya existente

# primera vez que subes la rama:
git push -u origin nombre-rama

❌ Error común: ! [rejected] ... fetch first. Significa que hay cambios en GitLab que tú no tienes.
✅ La solución es siempre la misma: git pull y después git push.

7️⃣ git switch -c


🔧 Qué hace

Crea una rama nueva y te cambia a ella. Una rama es una línea de trabajo paralela.

⏰ Cuándo se usa

Al empezar cualquier tarea nueva. Nunca trabajes directo en main.

git switch -c pantalla-login
git switch main
git branch

❌ Error común: hacer commits en main sin darse cuenta, o crear la rama después de trabajar.
✅ Antes de escribir código: git status para confirmar en qué rama estás.

¿Para qué sirven las ramas?


main es la versión que siempre funciona. Cada persona trabaja en su propia rama y, cuando algo está listo, se integra a main. Así nadie pisa el trabajo de nadie.

🌿 Nombres claros: pantalla-login, arregla-promedio, documentacion.

Bloque 3

Flujo básico individual

El flujo completo, de principio a fin



🔁 Este ciclo lo vas a repetir cientos de veces. Que se te haga automático.

Los pasos, con los comandos exactos


# 0. Una sola vez: traer el repositorio
git clone https://gitlab.usm.cl/grupo-07/proyecto-ads.git
cd proyecto-ads

# 1. Antes de empezar: traer lo que hicieron los demás
git pull

# 2. Crear tu rama para la tarea
git switch -c pantalla-login

# 3. ... programar ...

# 4. Revisar qué cambiaste
git status

# 5. Preparar y guardar
git add .
git commit -m "Agrega pantalla de login"

# 6. Subir tu trabajo
git push -u origin pantalla-login

Dos costumbres que evitan el 90 % de los problemas


1️⃣ git pull antes de empezar

Siempre. Antes de escribir la primera línea.

Así trabajas sobre la versión más nueva y evitas choques con tus compañeros.

2️⃣ Commits pequeños y seguidos

No esperes a “terminar todo” para guardar.

Un commit por cada cosa que funciona. Es más fácil volver atrás.

Si aparece un conflicto, no es un error


def promedio(notas):
<<<<<<< HEAD
    return sum(notas) / len(notas)
=======
    if not notas:
        return 0
    return sum(notas) / len(notas)
>>>>>>> mi-rama


Pasa cuando dos personas editaron la misma línea.

Git no puede adivinar cuál está bien, así que te pregunta a ti.


Qué haces: eliges qué código queda, borras las tres marcas, y haces git add + git commit.


💬 Si tienes dudas, habla con quien escribió la otra versión. Es una conversación, no una pelea.

Herramienta Para qué sirve en tu equipo

Issues: la lista de tareas del equipo


Un Issue es una tarea, un error o una idea.


Responde tres preguntas:

  • ¿Qué hay que hacer?
  • ¿Quién lo está haciendo?
  • ¿Ya está listo?


Se crea en: Issues → New issue

  El formulario acepta campos vacíos.
  Hay que mostrar un mensaje de error.

  - [ ] Mostrar mensaje al usuario

Merge Request: “revisen esto antes de integrarlo”


Un Merge Request dice:

“Trabajé en mi rama. Quiero que esto entre a main. ¿Lo revisan?”


Sirve para:

  • Ver exactamente qué cambió.
  • Comentar y sugerir mejoras.
  • Dejar registro de por qué se integró.
  • Que main no se rompa.

Revisar el código de un compañero


🔍 Qué mirar

  • ¿Entiendo qué hace?
  • ¿Hace lo que dice el Issue?
  • ¿Se le quedó algo a medias?
  • ¿Los nombres se entienden?

💬 Cómo comentar

Haz clic en el número de línea y escribe.

❌ “esto está malo”

✅ “¿qué pasa si la lista viene vacía? creo que falla acá”


🤝 Se revisa el código, no a la persona. Y revisar es la forma más rápida de aprender de tus compañeros.

¿No tienes Git instalado? Hazlo desde la web


Todo lo anterior se puede hacer sin instalar nada, desde el navegador:

  1. Entra al proyecto en GitLab y abre la carpeta integrantes/.
  2. Botón + → New file. Nómbralo nombre-apellido.md.
  3. Escribe tu contenido en el editor web.
  4. Abajo, en Commit message, escribe un mensaje claro.
  5. Elige “Create a new branch” y ponle tu nombre.
  6. Marca ✅ “Start a new merge request with these changes”.
  7. Botón Commit changes → se abre el Merge Request solo.


💡 Es exactamente el mismo flujo: rama → commit → Merge Request. Solo cambia dónde lo escribes.

Uso responsable de IA

La IA te puede ayudar mucho con Git


Para qué Ejemplo de lo que le puedes pedir
Entender un error “¿Qué significa este error de Git? ¿Cómo lo soluciono?”
Redactar un commit “Escribe un mensaje de commit corto y claro para estos cambios”
Mejorar un Issue “Reescribe este Issue para que quede claro qué hay que hacer”
Resumir un MR “Resume qué cambia este Merge Request y qué debería revisar”
Entender un conflicto “Explícame qué hacía cada versión de este conflicto”
Entender un comando “¿Qué hace exactamente este comando? ¿Qué riesgo tiene?”


💡 Especialmente útil al principio: pídele que te explique el error antes de ejecutar nada.

Cuatro advertencias


🔓 Nunca pegues contraseñas, tokens ni credenciales en una herramienta de IA.

🧠 No entregues código que no entiendes. Si no lo puedes explicar, no lo subas.

🔍 Verifica siempre. La IA inventa comandos que no existen, con total seguridad.

⚖️ La responsabilidad final es tuya, no de la herramienta.


✅ Usar IA no está penalizado. Entregar algo que no entiendes, sí.

Cierre

Para llevarte

Lo más importante de todo


En Git casi nada se pierde.


Si hiciste un commit, tu trabajo está a salvo.
Siempre hay forma de volver.


  • El miedo típico es “voy a romper el repositorio”. Es muy difícil romperlo de verdad.
  • Lo peor que suele pasar es que quede desordenado — y eso se arregla.
  • Ante la duda: pregunta antes de ejecutar. No hay preguntas tontas con Git.

Errores típicos y qué hacer


😬 Te pasó esto 🛠️ Haz esto
Cambiaste un archivo y quieres dejarlo como estaba git restore archivo.py
Hiciste git add de algo que no querías git restore --staged archivo.py
El mensaje del commit quedó malo (y aún no hiciste push) git commit --amend -m "mensaje nuevo"
git push rechazado: “updates were rejected” Primero git pull, después git push
Apareció un conflicto Elige qué versión queda, borra las marcas, y haz commit
Crees que perdiste commits git reflog — casi siempre están ahí


🚨 Los únicos dos comandos que sí pueden borrar trabajo: git reset --hard y git push --force. No los uses sin preguntar.

Chuleta: todo en una diapositiva


Empezar

git clone URL          # traer el repo
git config --global user.name "..."

Todos los días

git pull               # antes de empezar
git status             # ¿qué cambié?
git add .              # preparar
git commit -m "..."    # guardar
git push               # compartir

Ramas

git switch -c mi-rama          # crear
git switch main                # cambiar
git branch                     # listar
git push -u origin mi-rama     # subir

Si algo sale mal

git restore archivo            # descartar cambios
git restore --staged archivo   # sacar del staging
git log --oneline              # ver la historia
git reflog                     # recuperar
